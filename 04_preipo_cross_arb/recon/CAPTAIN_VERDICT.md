### 0.1 你问的「增大利润还是减少利润」——**在唯一可验证的样本上是减少；且尾部风险单向变大**

拆成四个**互相独立、方向不同**的作用（你原文把它们写在一起，这是最危险的地方）：

| # | 作用 | 对期望利润 | 对尾部风险 | 裁决 |
|---|---|---|---|---|
| ① | 限价单 + 较小容差 | 容差上限 τ* = **2.33 bps**（纯费差口径）；代码 `MAX_SLIPPAGE_BPS = 5.0` 已在 τ* 之上 → 每笔净亏 **2.67 bps**。**但若实测点差 ≥5 tick，τ* 升到 4.5~6.6 bps，5 bps 反而变合理** → 必须先实测 | 无 | **参数待定，必须先测 S 与 markout** |

## 1. 对账架构裁决（这才是要落地的东西）

### 1.1 唯一权威：Hedge Ledger，存「目标」不存「增量」

```
q_HL   : HL 带符号持仓（股）        q_OKX : OKX 带符号持仓（张）
S      : 股本基准（必须与结算 rebase 用同一个数）

spc         = S / 10B                   // 股/张。S=12.7 → 1.27（★不是 0.7874）
target_okx  = -q_HL / spc               // 我方希望的 OKX 持仓
residual    = target_okx - q_OKX        // 还需发出的订单（带符号）
naked       = q_HL + q_OKX * spc        // ★股等价裸敞口
```

**为什么是 target 不是 delta**：增量账本在「对冲已发出但 ack 丢失」时会重复发单，原单随后也成交 →
仓位翻倍而系统以为已平。`residual` 由两条腿实际持仓重算，晚到的成交已经把 residual 缩小，
**任何 ack 到达顺序都不会翻倍**。

**★ 最容易被写错的一行**：`10/S = 0.7874` 是「每 1 股需要几张」，**不是**「1 张等于几股」。
1 张 = S/10 = **1.27 股**。写成 0.7874 会让 `naked` 在完美对冲时等于 +0.72 股，
守卫会永久误报裸敞口并反复触发平仓 —— 这个错误我已经在自测里复现并修掉（见 §5.1 断言 1）。

**另：`naked ≠ residual`**。`10/S ≠ 1` 时完美对冲的 `q_HL + q_OKX` 恒不为 0，
所以裸敞口必须换算成股等价，`dust` 也必须用股等价（**0.001 股**：max(HL lotSz 0.001 股, OKX 0.001 张 × 1.27 = 0.00127 股)）。

### 1.2 状态机（禁止用布尔近似）

| 状态 | 允许开新仓 | 允许动作 | 出口 |
|---|---|---|---|
| `FLAT` | ✅ | 正常报价 | 两腿股等价均为 0（dust 内） |
| `OPENING` | ❌ | 只完成本轮 Leg 2 | 完成 → `HEDGED`；超预算 → `ORPHAN_*` |
| `HEDGED` | ✅ | 正常报价 | `|residual| > dust` → `UNDER/OVER` |
| `HEDGE_PENDING` | ❌ | 只发/重发 residual | residual≈0 → `HEDGED`；尝试用尽 → `HALT` |
| `OVERHEDGED` | ❌ | **只减少超额那条腿** | 回 `HEDGED` |
| `UNDERHEDGED` | ❌ | **只补足欠缺那条腿** | 回 `HEDGED` |
| `ORPHAN_SUSPECT` | ❌ | **只读**，三重确认 | 确认为真 → `ORPHAN_CONFIRMED`；读到非零 → 回 `HEDGED` |
| `ORPHAN_CONFIRMED` | ❌ | 按 §1.4 三分支处置 | 两腿归零 → `FLAT` |
| `CLOSING` | ❌ | 双腿平仓事务，只重试失败腿 | 两腿真实为 0 → `FLAT`；超时 → `HALT` |
| `HALT` | ❌ | 无（人工） | 人工确认复位 |

### 1.3 「空列表 ≠ 零持仓」——R6 的直接死因

`q = 0` 只有在**全部**满足时成立，否则该腿一律 `UNKNOWN`：

1. HTTP 成功 **且** 交易所 `code == 0`（HL 侧：返回体必须同时含 `marginSummary` 与 `assetPositions`，缺一即判结构异常）
2. 连续 **3 次**读取、间隔 **1.0 s**，结果一致（3 次滤单点抖动，1 s 跨过 HL 出块 ~250ms 与 OKX 推送节拍）
3. 该标的**无在途挂单、无在途撤单**
4. `positions-history`（OKX）/ `userFills`（HL）**能解释**仓位为何消失

任一不满足 → `UNKNOWN` → **禁止平掉另一腿**。这条若在 01:39 生效，R6 不会发生。

> **另一个必须写进代码注释的坑**：HL `clearinghouseState` **必须带 `"dex": "xyz"`**。
> 不带 dex 返回的是主池（实测 `accountValue: 0.0`），带 `dex=xyz` 才返回隔离池。
> 这个差异会让「读不到」看起来像「零持仓」，是同一类 fail-open。

### 1.4 单腿异常三分支（把「猜」换成查表）

| 分支 | 现场 | 动作 | 上限 |
|---|---|---|---|
| **A** | 一腿股等价 = 0，另一腿 ≠ 0，**无**在途平仓单 | **立即平掉幸存腿** → `FLAT` | 滑点 ≤ 10 bps，1 次，5 s，失败 → `HALT` |
| **B** | 一腿 = 0，另一腿**正在**平仓 | 等该单**终态**（不是在等「另一腿自然平完」） | ≤ 5 s；超时改市价；再失败 → `HALT` |
| **C** | 两腿都有仓但数量不匹配 | **只交易 `residual`**，不猜「该留哪条腿」 | 同 A 的上限 |

分支 C 的正例就是 17:04 那次：HL 0.91 股 / OKX 空 2.575 张 → `residual = +1.8585 张` → 买回 1.8585 → 留 0.7165 张配对。
**这个动作当时是对的，修 bug 时不要把它一起改掉。**

分支 A 的唯一例外（默认关闭、需显式开启）：确认是瞬时撮合缺口且价差仍满足开仓门槛 → 补开缺失腿；
必须同时满足滑点 ≤ τ*（实测后确定，暂定 2.33 bps）、尝试 ≤ 3 次、总时长 ≤ 5 s，任一越界立刻回落到「平幸存腿」。

### 1.5 平仓是「双腿事务」

- `close_intent` 先落盘（两腿都有记录）→ 两腿（近）同时发单 → 一腿失败**只重试失败腿**
- **只有两腿真实持仓都为 0 才置 `FLAT`**
- 超时 → `HALT` + 告警
- **「只平了一条腿却打印『双腿平仓完成』」这一行必须从代码里删掉**

### 1.6 启动对账（起来先别交易）

```
1) HALT，暂停一切开仓
2) 撤销本策略全部挂单，等每张单进入终态
3) 连续 3 次 × 1s 读两所持仓（HL 必须带 dex=xyz）
4) 校验读数稳定且结构完整（§1.3 的 1~3）
5) 计算 target / residual / naked（股等价）
6) 分类：FLAT / HEDGED / UNDER / OVER / ORPHAN_SUSPECT
7) 只执行一次修正（分支 A/B/C 查表）
8) 重读确认（回第 3 步，最多 2 轮）
9) 第 7 或 8 步失败 → 保持 HALT，告警，不交易
10) 通过后才解除 HALT 进主循环
```

### 1.7 独立对账器 + **时间维度**止损

- 独立进程，周期 **5 s**（短于最坏 `T_max`），用本地 SQLite/文件与主循环通信（不用内存共享：主循环崩溃后状态不能丢）
- 分级：`WARN` → `FREEZE_NEW` → `FLATTEN` → `KILL`
- **必须补时间维度裸持止损**（比价格维度有效 3 个数量级）：

| 裸持时长（股等价 > dust 且无在途对冲单） | 动作 |
|---|---|
| > **60 s** | 告警 + `FREEZE_NEW` |
| > **180 s** | 授予 `FLATTEN` 权限：自动跑 A/B/C 阶梯 |
| > **600 s** | `HALT`（全撤 + 双腿平 + 停服 + 告警） |

**这三个数不是拍的，是按「尾部」而不是「期望漂移」定的：**

- **为什么必须用时间**：R6 里价格只走了 1.44%/15.5h。要让 **16%** 单腿止损触发，按这个漂移率需要
  $16/1.44 \times 15.5\text{h} = 172\text{ h} = \mathbf{7.2\ 天}$。**价格维度在结构上抓不住慢速裸腿。**
- **为什么是 60 s**：引擎自己的设计意图是亚秒级对冲（60 ms STP 间隔、2.0 s WS 死区），
  R7 也是 01:41 开、01:42 平 —— 整轮在一分钟内完成。60 s 已是设计延迟的 ~30 倍，
  却比 R6 的 15.5 小时紧 **925 倍**。
- **为什么是 180 s 而不是立即**：按 R6 实测漂移，裸持 180 s 的期望损失约 **$0.009**，
  而立即市价平的滑点成本约 **$0.10** —— 等待便宜 11 倍。所以 180 s 在**期望**上不早，
  但在**尾部**上决定性提前。这是它成立的唯一理由。
- **为什么是 600 s**：分支 A 的硬上限 60 s、分支 B 的阶梯 90 s，到 600 s 时所有自动路径都跑过 ≥3 轮，
  仍不平就说明**补救机制本身坏了**，必须升级到人。

**另加一条价格维度抓不到的总闸门（账户级）**：
累计已实现 + 未实现亏损 > `min(两所权益)` 的 **5%** → `FREEZE_NEW`；> **10%** → `KILL`。
依据很直接：ANT 累计 −$4.48 / OKX 权益 $36.87 = **12.2%** —— **这个账户已经越过 10% 的 KILL 线**，
5%/10% 的闸门会让它在几天前就停下来。

现有的「16% 单腿价格止损」和「S 15.2 熔断」在 R6 里**一次都没触发** —— 15.5 小时里价格只走了 1.47%。
**价格维度永远抓不住时间维度的裸持。两套阈值并存，不是二选一。**

> **最后一条是最重要的设计修正**：Vike 敢让 fill stream 当唯一权威，是因为它读不到 in-flight；
> 我们**没有任何私有成交流**，照抄会同时失去事实源和意图源。
> 正确顺序是：**先用带三态的持仓快照建立事实基线（`ok / ts / reason`），再用账本表达意图，冲突即 fail closed**；
> 等私有 WS 订单频道（HL `userFills`、OKX 私有 `positions`/`orders`）上线后，再把权威迁移到 fill stream。

**另一条对本题的更正**：HL 的 HIP-3 `xyz:*` 资产可能带 `onlyIsolated` / `strictIsolated`，
即 **「双边都是 10x cross、保证金占用对称」这个前提只对 OKX 成立**，HL 腿实际是隔离池（权益 $39.69）。
`§2.3` 的「各自 50% 保证金」因此要按「OKX cross + HL isolated」分别验证，不能假设对称。

### 1.9 对账器要比什么（12 项）与最锋利的一条

R6 的根治不在"多读几次持仓"，而在**换一个独立事实源**。按强度从高到低：

| # | 比对项 | 为什么它比"再读一次持仓"强 |
|---|---|---|
| **1** | **成交隐含持仓**：`Σ signed fills since 上次确认归零` 必须等于当前 `pos` | ★**最强**。它不依赖任何快照端点，快照说 0、成交链说 −1.858 时以成交链为准 —— 这正是 R6 的胜负手 |
| **2** | **HL `startPosition` 链式校验** | ★ Hyperliquid 免费送的精确不变式：`下一条.startPosition == 上一条.startPosition + signed_sz`。**链断 = 有成交没收到 = UNKNOWN，绝不是 0** |
| 3 | `positions` vs `account-position-risk.posData`（独立端点） | 两个端点同时错才可能一起骗过我们 |
| 4 | `orders-pending` vs 账本在途集合 | 出现"我们没发过的单"→ `HALT` |
| 5 | **`orders-algo-pending`（全部 ordTypes）** | 一张游离的条件单/OCO 止损可以**静默平掉一条腿** —— 这类成交不会走普通下单路径 |
| 6 | `bills.subType ∈ {100,101,104,105,125,126,127,128}` | 命中即**强平/部分强平/ADL**，策略假设作废 → `KILL` |
| 7 | `positions-history.type ∈ {3,4,5}` | 同上 |
| 8 | 每个 `clOrdId`/`oid` 的在途状态回查 | 超时**先查后发**，不直接重发 |
| 9 | `/api/v5/public/time` 与本地时钟偏差 | >5 s `WARN`；>30 s `FREEZE_NEW`（30 s 正是 OKX 请求过期窗口，超过后每个签名请求都失败） |
| 10 | `/api/v5/system/status` | 非 normal → 所有读数视为 stale |
| 11 | 权益 vs 账本预期 | 无成交却掉权益 = 有未建模的费用/资金费/清算 |
| 12 | 对账器心跳 | 判决行超过 `3 × 周期`（90 s）未更新 → 主循环自动 `FREEZE_NEW`，让"对账器死了"成为安全事件而不是静默事件 |

**判决分级（避免要么不管要么停机）**：

| 级别 | 触发 | 动作 |
|---|---|---|
| `WARN` | 单周期读数不一致且下周期自愈；时钟偏差 5–30 s | 仅日志 + 计数 |
| `FREEZE_NEW` | 连续 2 周期不一致；任一腿 `unknown`；时钟 >30 s；无法解释的权益跌幅 >5%；`RESIDUAL` 越带 >60 s | **禁止开新仓**，允许完成当前对冲 |
| `FLATTEN` | `ORPHAN_CONFIRMED`；裸持计时超限；`RESIDUAL` 越带 >120 s | 授权跑 A/B/C 阶梯（一律 `reduceOnly`） |
| `KILL` | 强平/ADL 命中；出现未发过的单或仓；两腿同时 `unknown` >5 min；鉴权失败 >60 s；存储不可写 | 全撤 + 双腿平 + 停服 + 告警，需人工重启 |

**对账器只能读 + 判决 + 平仓，永不建仓。** 这样它的 bug 爆炸半径被限制在"停手/平仓"，不可能"开出一条新裸腿"。

**跨进程通信**用本地 SQLite（WAL、`busy_timeout=3000`），不用内存共享：
主循环崩溃后证据要存活；1 核机器上跨进程也共享不了 Python 对象；
WAL 允许一写多读，正好是"主循环写意图/订单/成交，对账器写判决，双方互读"。
另外原子写一份 `recon_status.json`（tmp + `os.replace`），方便 SSH 直接 `cat`。

## 2. 你方案四项的逐项量化

### 2.1 限价 + 容差：τ* 要先测点差才能定

**先把「tick 尺度」从推测变成实测**（`meta`/`instruments` 直接查得）：

| 场所 | 实测常量 | 折算 |
|---|---|---|
| HL `xyz:ANT` | `szDecimals = 2`（**最小下单步长 0.01 股**）、`maxLeverage = 10` | 价格按 **5 位有效数字** → tick 随价位跳变 |
| OKX `ANTHROPIC-USDT-SWAP` | `tickSz = 0.01`、`lotSz = 0.001`、`minSz = 0.001`、`ctVal = 1`、`lever(max) = 20` | 1 tick = 0.01/138.43 = **0.722 bps** |

**HL tick 的隐阱（必须写进代码）**：5 位有效数字规则使得价位跨过 100 时 tick 会**跳 10 倍**：

| HL 价位 | tick | 折算 |
|---|---|---|
| $98.40 | 0.001 | **0.102 bps** |
| $99.99 | 0.001 | 0.100 bps |
| **$100.00** | **0.010** | **1.000 bps**（跳 10 倍） |
| $116.30 | 0.010 | 0.860 bps |

所以「1~2 个 tick 的容差」在 HL 上是 **0.1~2 bps 摇摆的量**，不可用 tick 数表达，**必须用 bps 表达**。
τ* = 2.33 bps 在当前 $98 处 ≈ **23 个 HL tick**，而在 $116 处 ≈ **2.7 个 HL tick**。

单 clip（HL 0.10 股 × $98.40 + OKX 0.0787 张 × $138.4296 = 合计 **$20.78**）：

| 组合 | 单边 bps | 往返 bps | 往返 $ |
|---|---|---|---|
| 双腿全 Taker | 3.027 | 6.053 | 0.01258 |
| 双腿全 Maker | 0.695 | 1.390 | 0.00289 |
| HL Maker + OKX Taker | 1.748 | 3.496 | 0.00727 |
| HL Taker + OKX Maker | 1.973 | 3.947 | 0.00820 |

单边费差 **Δf = 2.331 bps = $0.004845/clip**。

$$\tau^*_{leg} = S_{leg} - AS_{leg} + \Delta f_{leg}$$

| 假设点差 S | AS 假设 | τ*(加权) |
|---|---|---|
| 0 bps | — | **2.33 bps** |
| 2.03 bps（2 tick） | 0 | **4.05 bps** |
| 2.03 bps | S/2 | **3.19 bps** |
| 5.08 bps（5 tick） | S/2 | **4.48 bps** |
| 5.08 bps | 0 | **6.64 bps** |

**所以「5 bps 容差对不对」完全取决于实测点差与 markout**：
- 若点差只有 1~2 tick → 5 bps 已越界，每笔净亏 **2.67 bps**
- 若点差 5 tick 以上（盘前薄簿很可能） → 5 bps 反而太紧
- tick 尺度：HL `$0.01/$98.40 = 1.016 bps`，OKX `$0.01/$138.43 = 0.722 bps` → τ*=2.33 bps ≈ **2.3 个 HL tick / 3.2 个 OKX tick**

**费率不对称，别平均用力**：HL maker 是**返佣**（−0.2 bps），OKX maker 是**收费**（+1.5 bps）。
HL 侧挂单的边际价值（2.7 bps）比 OKX 侧（2.0 bps）高 35%，而 OKX 腿名义更大 —— **两腿都挂单是错的优先级**。

### 2.2 时间阶梯：可用时长只有「亚秒到 5 秒」

$$0.7979\cdot\sigma_{1s}\sqrt{T} = \tau \Rightarrow T_{\max} = \left(\frac{\tau}{0.7979\,\sigma_{1s}}\right)^2$$

两边名义 $N$ 同时出现、可约掉 → **结论与仓位大小无关**。σ 用两个独立口径交叉：

| 口径 | σ₁ₘᵢₙ | T(τ=1.0) | T(τ=2.33) | T(τ=5.0) |
|---|---|---|---|---|
| 实测 6h / 360 根 1m K 线（quiet） | 10.24 bps | 0.90 s | **4.88 s** | 22.5 s |
| 事故段 7min 位移（pulse） | 23.2 bps | 0.18 s | **0.95 s** | 4.45 s |
| OKX 925min 净漂移（下界） | 4.8 bps | 4.1 s | **22 s** | 103 s |

**但「能等多久」不等于「该等多久」** —— 还要乘以成交概率。按库存成本 / 单边费差 = 2.33 bps 反解所需成交率：

| 阶梯档位 | 库存成本（σ=23.2） | 所需挂单成交率 |
|---|---|---|
| 2 s | 1.68 bps | **≥ 52.5%** |
| 4 s | **2.37 bps** | **> 100%（已亏）** |
| 5 s | 2.65 bps | **≥ 83%** |
| ≥10 s | — | **数学上不可能** |

**裁决**：pulse 态下 4 秒档已经亏，2 秒档要求一半以上挂单成交 —— 这在盘前薄簿上做不到。
**用 0.1 s 的 IOC 补齐替代时间阶梯**：库存成本从 2.37 bps 降到 **0.37 bps**（同一公式，T=0.1s）。

## 4. 方向一致性问题（必须你确认，否则后面全白做）

`HEDGE_RATIO = 10/12.7 = 0.7874` 隐含 **S = 12.7B**。但在这个 S 下：

$$P_{\text{OKX, per share}} = 138.43 \times \frac{10}{12.7} = \$109.00 \;>\; P_{\text{HL}} = \$98.40$$

即 **OKX 比 HL 贵 10.8%**。此时「做空 HL + 做多 OKX」是**买入贵的、卖出便宜的** —— 这是**做多基差**，
只有基差**继续扩大**才赚钱（与你说的「点差扩大获利」一致），**不是收敛套利**。

方向要变成收敛套利需要：

$$S > \frac{10 \times 138.43}{98.40} = \mathbf{14.07\ B}$$

**所以：**
- 若你认定 S ≈ 16.9B（完全稀释） → OKX 折合每股仅 $81.91，**HL 贵** → 做空 HL / 做多 OKX 是**正确的收敛套利**，
  但**对冲比例应该用 10/16.9 = 0.5917，不是 0.7874**，否则系统性欠对冲 13%
- 若你认定 S ≈ 12.7B → 这个方向是**做多基差的方向性押注**，必须按方向性交易的仓位与止损管理

**同一套系统里，方向和 hedge ratio 必须用同一个 S。** 另外 worker 提出的开放问题值得单独立项：
**若 OKX 的 rebase 是「ctVal 等比调整 + 价格等比调整」，则整条价差的 P&L 连续，这个策略从头到尾就是纯基差方向交易，而不是套利。** 这条需要拿 OKX rebase 规则公告核实。
